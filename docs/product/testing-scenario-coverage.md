# 客户端测试场景覆盖盘点（分层与缺口）

> 文档状态：Draft
> 更新日期：2026-08-25
> 关联：[能力路线图](./capability-roadmap.md)（§4.4 Skill 扩展与管理）· [Capability 模型](../architecture/capability-model.md)

## 1. 目的

回答一个问题：**客户端测试场景需要多少新代码？**

本文档穷举移动端（Android）客户端测试场景，按支持方式分层归位，作为
「Skill 扩展与管理」元能力（路线图 §4.4）的立项依据与原语缺口清单。
本文档是需求侧盘点，不做实现承诺；任何缺口进入开发仍须走路线图 §5 的固定路径。

## 2. 分层定义

- **层 0 · Agent 循环**：一次性、长尾意图，模型直接编排既有能力，零新产物。
- **层 1 · 声明式 Skill**：可复用、要求可复现的场景，用受限 DSL 编排已登记
  Tool/Capability（selector、动作序列、循环、时长盒、断言），Runtime 解释执行，
  无代码评审。依赖路线图 §4.4「Skill 扩展与管理」元能力。
- **层 1+ · Runtime 本地扩展**：不触碰设备信任面的本地计算（如截图 diff），
  只需 DSL 断言类型扩展。
- **层 2 · 编码 Capability/原语**：触及新设备原语或新信任边界，必须独立迭代 +
  评审，Medium 以上风险另需 ADR。
- **平台层**：多设备调度等 V2 平台能力，不是逐场景写代码。
- **边界外**：不属于设备操作 Agent 的职责，或 C 档红线（路线图 §4.3）。

### 3.2 稳定性与健壮性

| 场景 | 层 | 依据 / 缺口 |
| --- | --- | --- |
| 长时间 soak / 遍历稳定性 | 1 | 纯编排（首驱动场景） |
| 崩溃 / ANR 检测与复现 | 1 | 前台巡检 + logcat 崩溃模式 |
| 内存泄漏粗判（曲线持续增长） | 1 | performance 时间序列 |
| 前后台切换 / 进程回收后恢复 | 1 | home + launch + state.inspect |
| 中断测试（来电/闹钟/其他 App 打断） | 2 | 需「模拟中断注入」原语；信任面中等 |
| 弱网 / 断网 / 超时重试 | 2 | 射频开关 B 档已有；网络整形（限速/丢包）是更重的新原语 |

## 4. 统计与结论

- **层 0/1 直接覆盖：约 60%**（27/45 条）；含层 1+ 本地扩展后约 **65%**。
- **层 2 新原语缺口收敛为约 8 个**：gfxinfo 帧率、启动耗时解析、流量统计、
  显示/方向设置写、网络整形、抓包/证据接入、模拟中断注入、mock location。
  其中 4 个的相关条目已在路线图 B 档登记（Deep Link、射频开关、短信只读、剪贴板）。
- **3 条明确不做**：预置权限拒绝、静态安全、低电量/低存储注入（C 档红线或不可行）。

**结论**：客户端测试全景 ≠ 逐场景功能迭代，而是
**「1 个 Skill 扩展与管理元能力 + ≤8 个按需评审的原语迭代 + 1 个多设备平台能力」**。
DSL 层一次解锁约 27 个场景；客户端测试场景的「可复现性」要求与声明式 Skill
天然匹配（自由 Agent 循环决策路径不可复现，测试报告不可比），这是该元能力的
立项量化依据。

## 5. 使用方式

- 新场景进入讨论时，先按 §2 归层；层 1 场景不产生迭代，只产出 DSL 技能定义。
- 层 2 缺口按路线图 §5 固定路径逐个评审，需求拉动，不提前囤货。
- 本表随真实任务暴露持续回填；归层判断变化时记录理由。
