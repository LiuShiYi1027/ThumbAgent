# Mobile Agent 第一版产品方案

> 状态：Active  
> 版本：V1.0  
> 更新日期：2026-07-03  
> 关联文档：[产品定位](./positioning.md)

## 1. 方案摘要

Mobile Agent 第一版采用“Skills 核心 + 本地桌面工作台 + 开放接口”的产品形态。

第一版只实现单台 Android 设备的完整闭环，但从协议和模块边界上为 iOS、鸿蒙预留平台适配能力。

用户能够连接一台 Android 设备，在桌面工作台中通过自然语言或确定性工具执行任务，并实时看到设备画面、动作过程与验证结果。外部 AI Agent 可以通过 Skills/MCP 或本地 API 调用相同能力。

第一版需要证明的核心假设是：

> 用户不必编写自动化脚本，也能让 AI 在真实设备上可靠地完成简单任务，并清楚知道它做了什么、是否成功以及为什么失败。

## 2. 产品形态

### 2.1 Skills：核心产品

Skills 将设备能力封装为 AI 可以发现、理解、组合和安全调用的目标级能力。每个 Skill 必须包含：

- 名称与自然语言描述
- 输入和结构化输出
- 支持的平台及能力要求
- 风险等级与确认策略
- 执行逻辑
- 结果验证
- 错误分类与证据

Skill 不等于底层命令。它描述用户目标，并负责调用工具、处理平台差异和验证结果。

### 2.2 Desktop Workbench：官方工作台

桌面端承担：

- 设备发现、连接和状态展示
- 自然语言任务输入
- 实时设备画面与人工接管
- Agent 执行过程展示
- 风险授权和确认
- 日志、截图与执行报告查看
- 模型、设备工具链和隐私设置

桌面端不是独立实现另一套业务逻辑，而是调用同一个本地核心服务与 Skills。

### 2.3 开放接口

第一版提供本地 API，并设计 MCP/CLI 接口边界。开放接口用于：

- 接入 Codex、Claude Code 等外部 AI Agent
- 接入 IDE 和开发者工作流
- 自动化脚本与 CI/CD
- 为后续团队版和企业系统集成奠定基础

V1 的完整体验以桌面端为主；MCP 可作为紧随其后的开发者预览能力。

## 3. 目标用户与首要任务

### 3.1 目标用户

第一版服务于：

- Android 开发工程师
- 测试工程师和 QA
- 独立开发者与小型 App 团队

### 3.2 首要用户任务

当用户需要临时操作、验证或检查一台 Android 设备时，可以直接描述目标，无需编写 ADB 或 UI 自动化脚本。

首版标杆任务：

> 连接 Android 设备，打开系统设置，并验证设置应用已成功进入。

扩展示范任务：

> 打开设置，进入网络页面，找到 Wi-Fi 设置；不要修改系统开关，完成后输出操作步骤与截图。

## 4. 核心概念模型

### 4.1 Tool

Tool 是确定性的原子设备能力，例如：

- 获取设备列表
- 获取截图
- 获取 UI 树
- 点击坐标或元素
- 输入文本
- 滑动
- 返回和 Home
- 启动应用

Tool 不负责理解复杂用户目标。

### 4.2 Skill

Skill 是面向目标的能力，由一个或多个 Tool、判断逻辑和验证逻辑组成，例如：

- 发现设备
- 观察当前屏幕
- 打开指定应用并验证
- 与当前页面交互
- 执行一个简单移动任务

### 4.3 Workflow

Workflow 是多个 Skills 的可复用编排。V1 记录任务轨迹，但暂不提供完整的可视化 Workflow 编辑器。

## 5. V1 首批 Skills

### 5.1 `discover_devices`

发现本机可连接的移动设备。

输出包括设备 ID、平台、连接状态、型号、系统版本和可用能力。V1 只返回 Android 设备，数据结构保留其他平台字段。

### 5.2 `inspect_device`

读取指定设备的基础信息和当前状态，包括屏幕尺寸、系统版本、当前前台应用和屏幕是否可交互。

### 5.3 `observe_screen`

获取当前截图、UI 树、前台应用和时间戳，形成一次标准化 Observation。

### 5.4 `open_app`

根据应用标识或系统应用名称启动应用，并通过前台包名或界面状态验证结果。

### 5.5 `interact_with_screen`

在当前页面上执行点击、输入、滑动、返回和等待。优先使用 UI 元素语义定位，坐标作为兜底。

### 5.6 `execute_mobile_task`

接收简单自然语言目标，循环执行“观察—决策—动作—验证”，直到任务完成、失败、超时或需要人工介入。

### 5.7 `capture_evidence`

保存任务关键节点的截图、当前应用、设备状态和操作记录。

### 5.8 `generate_execution_report`

输出任务目标、设备信息、动作时间线、关键证据、最终状态和错误原因。

## 6. V1 功能范围

### 6.1 必须实现

- 自动发现通过 ADB 连接的 Android 真机或模拟器
- 显示设备状态与基本信息
- 获取设备截图和 UI 树
- 启动系统应用或已知包名应用
- 点击、输入、滑动、返回、Home 和等待
- 用户输入简单自然语言任务
- Agent 逐步执行，每轮动作后重新观察
- 任务暂停、取消和人工接管
- 风险动作拦截
- 保存任务记录和关键截图
- 输出成功、失败或需要介入的明确结果
- 提供确定性的手动工具入口

### 6.2 可以延后

- 连续视频流和高帧率远程控制
- OCR 与复杂纯视觉定位
- APK 安装、卸载和清除数据
- Logcat 实时分析
- CPU、内存、帧率和耗电采集
- 工作流编辑器
- 多设备并行执行
- 团队空间和云端同步
- iOS 与鸿蒙真实适配器

### 6.3 明确不做

- 支付、转账和下单
- 自动处理密码与验证码
- 绕过系统权限或应用风控
- 无确认删除用户数据
- 任意 Shell 命令执行
- 承诺所有 App 和所有页面均可操作

## 7. 桌面工作台信息架构

### 7.1 首页 / 设备连接

页面目标是让用户确认环境是否可用。

展示：

- 已发现设备
- 设备平台、型号、系统版本和连接状态
- ADB 环境诊断
- 连接帮助和刷新按钮

### 7.2 任务工作台

采用三栏布局：

```text
┌────────────────┬────────────────────────┬─────────────────────┐
│ 设备与历史任务 │ 设备画面               │ Agent 工作区        │
│                │                        │                     │
│ 当前设备       │ 当前截图               │ 任务输入            │
│ 连接状态       │ 点击位置标记           │ 执行计划            │
│ 历史任务       │ 人工操作入口           │ 动作时间线          │
│                │                        │ 结果与异常          │
└────────────────┴────────────────────────┴─────────────────────┘
```

关键操作：

- 输入任务
- 开始执行
- 暂停 / 继续
- 停止任务
- 接管设备
- 查看单步截图和动作详情

### 7.3 任务报告

报告包括：

- 原始任务目标
- 设备与运行环境
- 开始、结束时间和耗时
- 动作时间线
- 每一步的动作、依据和结果
- 关键截图
- 最终状态
- 失败原因和建议的下一步

### 7.4 设置

第一版设置包括：

- 模型服务配置
- 数据保存目录与保留周期
- 截图和任务记录开关
- 默认风险确认策略
- Android SDK / ADB 路径

## 8. 核心用户流程

### 8.1 首次使用

```text
打开应用
→ 检查 ADB 环境
→ 引导开启开发者模式与 USB 调试
→ 发现设备
→ 用户在手机上完成连接授权
→ 进入任务工作台
```

### 8.2 执行任务

```text
选择设备
→ 输入目标
→ 系统检查能力与风险
→ 展示简短计划
→ 用户开始执行
→ Observe / Act / Verify 循环
→ 成功、失败或请求人工介入
→ 生成任务报告
```

### 8.3 人工接管

Agent 无法判断页面、连续失败或遇到权限弹窗时暂停任务。用户可以完成一次人工操作，再将控制权交还给 Agent。接管过程必须进入任务记录。

## 9. 任务状态设计

任务状态统一为：

```text
draft
→ ready
→ running
→ paused / awaiting_confirmation / awaiting_user
→ unknown_outcome / succeeded / failed / cancelled / timed_out
```

每个状态都必须在界面和 API 中有明确含义，不能只输出模糊的自然语言描述。

`unknown_outcome` 表示动作可能已经发生但无法确认。系统必须停止后续写动作，先重新观察或请求用户介入，不得直接自动重试。

## 10. 风险与权限设计

### 10.1 风险等级

- Low：观察、截图、返回、打开应用等可逆操作，可自动执行。
- Medium：输入文本、修改普通设置等可能产生状态变化的操作，按用户策略确认。
- High：安装卸载、清除数据、账号与隐私修改等操作，必须明确确认。
- Prohibited：支付、验证码绕过、任意命令等，V1 禁止执行。

### 10.2 执行原则

- 模型只能调用注册的 Tools 和 Skills。
- 每次调用必须经过参数校验、能力校验和风险策略。
- 所有设备动作都绑定明确的设备 ID。
- 高风险确认必须展示即将执行的动作、目标设备和影响。
- Agent 不确定时停止，而不是猜测性执行。

## 11. 多平台设计要求

V1 虽然只实现 Android，但上层协议不得暴露 ADB 特有概念作为通用接口。

统一设备模型至少包含：

```json
{
  "device_id": "string",
  "platform": "android | ios | harmonyos",
  "model": "string",
  "os_version": "string",
  "connection_state": "string",
  "capabilities": ["observe_screen", "launch_app"]
}
```

平台适配器必须声明能力矩阵。Agent 根据 capability 判断是否能够执行，不能假设不同平台能力完全一致。

后续规划：

- iOS：XCUITest / WebDriverAgent、Simulator、受信任真机和开发者签名能力。
- 鸿蒙：根据 HarmonyOS/OpenHarmony 目标环境接入对应测试、设备命令、Hilog 和包管理工具。

## 12. 技术产品边界

建议逻辑架构：

```text
Desktop Workbench / CLI / External Agent
                  ↓
        Local API / MCP Gateway
                  ↓
        Skill Registry & Runtime
                  ↓
  Policy Engine / Task Engine / Evidence Store
                  ↓
             Device Gateway
                  ↓
 Android Adapter / iOS Adapter / HarmonyOS Adapter
```

重要约束：

- Skills 与桌面界面解耦。
- Agent Core 与平台命令解耦。
- 平台能力通过适配器和 capability 暴露。
- 任务、动作、观察和证据使用结构化数据保存。
- 模型供应商可替换，设备执行不能依赖某个特定模型。

## 13. V1 验收场景

### 场景一：设备发现

连接一台已授权 Android 设备后，工作台能够在 5 秒内展示设备状态、型号和系统版本。

### 场景二：观察设备

用户点击刷新后能够看到当前截图、前台应用和 UI 结构，并带有一致的时间戳。

### 场景三：打开设置

用户输入“打开系统设置”，Agent 能启动设置应用，并通过前台包名或界面信息确认成功。

### 场景四：简单导航

用户输入“进入 Wi-Fi 设置页面，不要修改开关”，Agent 能完成导航、停在目标页面并遵守限制。

### 场景五：失败可解释

设备断开或目标元素不存在时，任务明确失败或请求用户介入，报告中包含失败步骤、错误信息和最后一次截图。

### 场景六：安全边界

任何未注册动作、任意 Shell 请求或被禁止动作都不能到达设备执行层。

## 14. V1 成功指标

- 标杆任务成功率不低于 90%
- 预定义简单导航任务成功率不低于 80%
- 设备断连和元素缺失能够被识别，不误报成功
- 100% 的设备动作有任务、设备、时间和结果记录
- 高风险或禁止动作未经授权执行次数为零
- 用户能够在任意执行步骤暂停或终止任务
- 新增平台适配器不需要修改上层 Skill 输入输出协议

## 15. 版本推进建议

### Milestone 1：确定性设备工具

完成设备发现、截图、UI 树、应用启动和基础交互，先通过手动工具箱验证设备层稳定性。

### Milestone 2：Agent 闭环

完成自然语言任务、单步决策、执行后观察、结果验证、停止与接管。

### Milestone 3：Skills 开放

稳定 Skill Schema、本地 API 和 Skill Registry，提供外部 Agent 调用示例。

### Milestone 4：工程能力扩展

加入应用安装、日志采集、诊断包和基础性能指标，为 iOS 与鸿蒙适配器原型做好准备。

## 16. V1 发布定义

第一版可以对外描述为：

> Mobile Agent Preview：一个本地运行的 Android 设备 Skills 平台。你可以在桌面工作台或 AI Agent 中用自然语言操作设备，实时观察过程，并获得可验证的执行结果。

V1 的成功不在于支持最多动作，而在于建立一个可靠、透明、可扩展的 AI-to-Device 闭环。
