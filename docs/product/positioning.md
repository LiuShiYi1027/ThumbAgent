# Mobile Agent 产品定位

> 文档状态：Active  
> 更新日期：2026-07-03

## 1. 一句话定位

Mobile Agent 是一个本地优先、面向 AI Agent 的跨平台移动设备 Skills 平台。它让 AI 能够安全、可靠地操作、测试和诊断移动设备，并生成可复现、可审计的执行记录。

首阶段从移动应用研发、测试和问题诊断切入，逐步覆盖 Android、iOS、鸿蒙及更多智能终端。

Skills 是产品核心；桌面工作台是官方提供的最佳使用、授权和观察环境；CLI、Local API 与 MCP 是面向其他 Agent 和工程系统的开放入口。

## 2. 我们要解决的问题

移动设备上的大量工作仍然依赖人工操作、零散脚本和彼此割裂的工具：

- 临时操作不值得编写自动化脚本，复杂脚本又需要较高的开发和维护成本。
- 固定坐标或固定元素定位容易受到页面改版、系统弹窗、机型和系统版本差异影响。
- 设备操作、日志采集、性能分析和问题诊断分散在不同工具中，问题发生后常常已经错过关键现场。
- 多台设备上的安装、配置、测试、巡检和信息采集会产生大量重复劳动。
- Android、iOS、鸿蒙拥有不同的工具链和权限体系，跨平台流程难以复用。
- 现有自动化系统通常只能执行预先编写的流程，无法理解目标、观察变化并自主恢复。

Mobile Agent 要将这些割裂的能力组织成一个完整闭环：

```text
自然语言目标
    → 任务规划
    → 设备操作
    → 状态观察
    → 结果验证与异常恢复
    → 日志、性能和截图等现场采集
    → 可复现、可审计的执行报告
```

## 3. 产品本质

我们不是单纯在做“会点击屏幕的 AI”。屏幕操作只是基础能力。

产品真正提供的是：

> 让用户用统一的方式，将目标安全、可靠地交给不同平台上的移动设备执行，并获得可信的结果和完整证据。

因此，产品价值由四部分构成：

1. **理解目标**：将自然语言转化为受约束、可执行的任务计划。
2. **操作设备**：结合系统语义、UI 结构和视觉信息完成设备交互。
3. **验证结果**：判断动作是否生效、任务是否完成，并在失败时尝试恢复。
4. **采集现场**：同步保存截图、日志、性能、设备状态和操作轨迹，辅助复现与诊断。

## 4. 目标用户

### 4.1 首批核心用户

- 移动端开发工程师
- 测试工程师与 QA 团队
- App 创业团队和独立开发者
- 管理真机实验室、兼容性测试平台或设备农场的团队
- 需要批量管理移动终端的企业技术团队

### 4.2 后续扩展用户

- 企业移动业务运营人员
- 售后、技术支持和远程诊断团队
- 需要跨 App 执行固定工作流的专业用户
- 在明确授权和安全边界下使用个人智能助理的消费者

首阶段不把支付、社交自动发布、账号安全操作等高风险消费场景作为重点。

## 5. 核心使用场景

### 5.1 智能操作与测试

用户描述目标，Agent 自主完成操作并验证结果，例如：

> 安装这个测试包，打开应用，进入设置，开启深色模式，返回首页并确认页面样式发生变化。

### 5.2 问题复现与现场采集

Agent 在执行复现流程的同时采集日志、截图、录屏、设备状态和性能数据，失败后生成诊断材料。

### 5.3 设备管理

在受控权限下完成应用安装、升级、卸载、启动、停止、清除数据、权限配置、文件传输和设备信息查询。

### 5.4 性能与稳定性分析

围绕指定应用或操作流程采集 CPU、内存、帧率、耗电、温度、网络、启动耗时、Crash 和 ANR 等数据。

### 5.5 多设备任务编排

将同一目标分发到不同厂商、系统版本和屏幕规格的设备上执行，统一汇总结果并对比差异。

## 6. 多平台战略

### 6.1 总体原则

产品从第一天就采用跨平台抽象，但不要求第一版同时完整支持所有平台。

核心 Agent 只理解统一的设备能力和动作协议，不直接依赖 ADB、XCTest 或鸿蒙工具链。平台差异由独立的设备适配器负责。

```text
Agent Core
    ↓
统一能力协议与安全策略
    ↓
Device Gateway
    ├── Android Adapter
    ├── iOS Adapter
    ├── HarmonyOS Adapter
    └── Future Platform Adapter
```

### 6.2 Android

Android 作为首个落地平台，原因是工具链开放、设备控制能力完整，适合快速验证产品闭环。

计划接入的能力包括：

- ADB
- UIAutomator / Accessibility
- 截图、录屏和 UI 树
- Logcat 与系统诊断信息
- APK 安装、卸载和包管理
- CPU、内存、帧率、耗电、网络等性能指标

### 6.3 iOS

iOS 通过独立适配器接入，主要考虑：

- XCUITest / WebDriverAgent
- Simulator 与受信任真机
- 应用安装、启动和 UI 自动化
- syslog、崩溃日志和 Instruments 性能数据
- 开发者签名、配对、权限和沙箱限制

iOS 的能力边界会明显受到系统安全机制和开发者授权影响。产品应明确呈现“不支持”“需要授权”与“允许执行”的差异，不能通过不可靠方式伪装能力一致。

### 6.4 鸿蒙

鸿蒙通过独立适配器接入，并区分具体系统和设备环境。重点关注：

- DevEco Testing / 测试框架与设备命令工具
- HAP 安装、卸载和应用生命周期管理
- UI 自动化与界面信息采集
- Hilog、故障日志与性能数据
- 系统版本、开发者模式及企业设备权限差异

在正式实现前，需要根据目标设备确认 HarmonyOS 与 OpenHarmony 的工具链、接口和权限边界，避免将两者笼统视为完全相同的平台。

## 7. 核心产品原则

### 7.1 本地优先

设备连接、动作执行、敏感信息和任务记录默认保留在本地。模型层采用可替换设计，支持本地模型，也允许用户显式配置受信任的云端模型。

### 7.2 安全优先

模型不能直接执行任意 Shell 命令，只能调用白名单内、具有明确参数和风险等级的设备动作。

以下动作默认需要用户确认：

- 安装、卸载或降级应用
- 清除应用或设备数据
- 修改账号、权限和安全设置
- 发送消息、发布内容或提交表单
- 付款、下单和其他不可逆业务操作
- 读取、输入或传输密码、验证码等敏感信息

### 7.3 结果可验证

每个动作执行后都必须重新观察设备状态。任务完成不能只依据“命令已经发送”，而应依据界面、系统状态或业务结果的变化。

### 7.4 全程可审计

记录任务目标、规划、动作参数、执行时间、设备响应、关键截图、异常和用户确认。敏感字段应脱敏，并支持按策略关闭或清理记录。

### 7.5 能力渐进增强

优先保证少量动作稳定可靠，再扩展复杂能力。无法确认时主动停止并请求用户介入，而不是冒险继续操作。

## 8. 第一版产品范围（MVP）

第一版聚焦单台 Android 设备，跑通最小闭环：

- 发现和连接设备
- 获取设备基本信息、当前应用、截图和 UI 树
- 支持打开应用、点击、输入、滑动、返回、Home 和等待
- 将自然语言目标转换为受限动作
- 每一步操作后重新观察并验证
- 支持超时、重试、任务取消和人工接管
- 保存任务轨迹、截图和执行结果
- 提供简单的本地 Web 控制台

第一版示范任务：

> 用户输入“打开系统设置”，Agent 识别设备、执行操作、验证当前应用，并展示完整操作轨迹。

随后逐步加入：

- 页面元素语义定位与视觉定位兜底
- APK 安装、卸载和应用生命周期管理
- Logcat 采集和诊断包导出
- 基础性能数据采集
- iOS 和鸿蒙适配器原型

## 9. 非目标

现阶段不追求：

- 无限制地操作所有设备和所有 App
- 首版同时实现 Android、iOS、鸿蒙的全部能力
- 绕过系统权限、安全机制、验证码或应用风控
- 在没有确认的情况下完成支付、删除数据等高风险动作
- 用完全自主替代可靠性、可观察性和用户控制

## 10. 差异化

与传统自动化工具相比，Mobile Agent 能理解目标、动态观察页面并在环境变化时调整路径。

与通用 AI 手机助手相比，Mobile Agent 更强调工程能力、跨平台设备控制、现场采集、结果验证和可审计性。

与设备管理平台相比，Mobile Agent 不要求用户预先编写每一条流程，而是允许用户直接描述目标，同时保留确定性的安全与执行边界。

我们的核心差异可以概括为：

> 自然语言驱动 + 跨平台设备能力 + 自主验证恢复 + 工程现场采集 + 本地安全边界。

## 11. 产品演进路线

```text
单台 Android 设备操作
    → 稳定的智能测试执行
    → 日志与性能诊断
    → iOS / 鸿蒙平台适配
    → 多设备任务编排
    → 本地智能设备实验室
```

### 阶段一：基础闭环

完成自然语言、设备观察、动作执行和结果验证。

### 阶段二：工程能力

增加日志、性能、包管理、文件和诊断能力，形成可用的 AI 设备工程师。

### 阶段三：跨平台

通过统一能力协议接入 iOS 和鸿蒙，明确各平台的能力矩阵与限制。

### 阶段四：规模化

支持多设备并行执行、任务调度、结果对比、团队协作和设备实验室管理。

## 12. 产品成功标准

首阶段重点衡量：

- 任务成功率
- 平均完成步数与耗时
- 动作定位成功率
- 异常恢复成功率
- 需要人工介入的比例
- 执行结果的可复现率
- 日志、截图和性能证据的完整度
- 高风险动作未经确认的执行次数必须为零
