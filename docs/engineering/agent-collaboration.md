# 多 Agent 协作规范

> 状态：Active  
> 更新日期：2026-07-03

## 1. 目标

让多个 Agent 在共享仓库中并行工作时保持边界清楚、结果可合并、责任可追踪。

## 2. 任务拆分

优先按稳定边界拆分：

- Contracts
- Domain 与状态机
- Android Adapter
- API/MCP Interface
- Desktop UI
- 测试与 fixtures
- 文档与 ADR

不要把同一个注册表、Schema 或迁移文件同时交给多个 Agent 修改。无法避免时指定唯一整合者。

## 3. 任务说明模板

每个任务至少说明：

```text
目标：最终需要产生什么行为
范围：允许修改的模块
非目标：明确不做什么
接口：依赖和提供的 Contract
验收：必须通过的测试或场景
风险：安全、兼容或并发注意事项
```

## 4. 开工协议

Agent 开工前：

1. 阅读根和目录级 `AGENTS.md`。
2. 检查 Git 状态和目标文件。
3. 确认现有修改归属，不覆盖未知改动。
4. 复述任务边界和关键假设。
5. 仅在需要时新增 ADR 或 Contract。

## 5. 修改规则

- 保持 patch 小而聚焦。
- 不顺手修复无关问题；记录后单独建任务。
- 不批量格式化未修改模块。
- 不重命名公共对象而不更新 Contract 和消费者。
- 不修改生成文件来源不明的内容。
- 不把临时调试开关或本机路径提交到仓库。

## 6. 并发冲突处理

遇到其他修改时：

- 能在不触碰对方区域的情况下继续，则缩小范围继续。
- 需要同一接口时，先协调 Contract，由唯一 Agent 修改真源。
- 不知道改动归属时停止覆盖性操作并报告。
- 不通过删除、回滚或强制重写解决冲突。

## 7. 交付协议

Agent 完成后必须报告：

```text
完成内容
修改文件
运行的验证及结果
未运行的验证及原因
已知限制或后续工作
```

不以“代码看起来正确”代替验证结果。

## 8. 评审协议

评审 Agent 以发现问题为主，不直接扩大修改范围。问题按以下优先级：

- P0：安全、数据损坏或不可逆设备影响
- P1：核心功能错误、状态不一致、边界绕过
- P2：兼容性、可维护性或测试缺口
- P3：非阻塞改进

评审结论必须引用具体文件和行为，避免纯偏好评论。

## 9. 共享知识

- 长期架构知识进入 ADR。
- 操作步骤进入工程指南。
- 临时发现进入任务或 Issue，不塞进代码注释。
- 新 Agent 应能只阅读仓库文档理解当前决策，不依赖聊天历史。
