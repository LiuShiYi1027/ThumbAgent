# 数据与迁移规范

> 状态：Active
> 更新日期：2026-07-03

## 1. 适用范围

包括 SQLite Schema、用户配置、Artifact 布局、缓存格式以及需要跨版本保留的本地状态。

## 2. 基本原则

- 所有持久化 Schema 变化必须有版本化迁移。
- 禁止在应用启动时执行未记录的临时 DDL。
- 迁移与应用代码在同一变更中提交。
- 用户数据和测试数据使用不同目录与数据库。
- 数据损坏时优先保护原始数据，不自动删除后“恢复正常”。

## 3. 迁移文件

- 使用递增 revision ID 和不可变迁移文件。
- 已发布迁移不得修改；修复使用新迁移。
- 每个迁移说明目的、前置版本、升级步骤和恢复策略。
- CI 从空数据库执行全量升级，并从受支持旧版本执行增量升级。

## 4. 兼容窗口

- Runtime 启动时检查数据库版本。
- 数据库过新时拒绝启动写模式，避免旧 Runtime 破坏数据。
- 数据库过旧时先备份并迁移。
- Desktop 与 Runtime 通过 API 版本协商，不直接读取数据库。

## 5. 迁移安全

迁移前：

1. 确认没有活动 Task。
2. 检查磁盘空间。
3. 创建可识别版本的备份。
4. 获得独占迁移锁。

迁移中：

- 尽可能使用事务。
- 大数据转换分批执行并记录进度。
- 不调用设备、模型或网络。
- 不把用户内容写入迁移日志。

迁移后：

- 执行完整性检查。
- 更新 Schema version。
- 失败时保留备份和可诊断错误。

## 6. 回滚策略

- 数据库结构 down migration 不是默认承诺。
- 优先采用前向修复。
- 发布前必须说明版本是否可降级。
- 不可逆迁移必须通过 ADR，并在执行前明确告知用户。
- 应用回滚若不兼容新数据库，应以只读或拒绝启动方式保护数据。

## 7. Artifact 一致性

- 数据库保存相对路径、类型、大小和 SHA-256。
- 文件先写临时路径并 fsync，再原子重命名，最后提交数据库引用。
- 数据库提交失败时清理孤立临时文件。
- 定期清理前先标记，再删除文件，最后删除引用。
- 发现缺失文件时记录 `ARTIFACT_MISSING`，不伪造空证据。

## 8. 保留与清理

- 默认保留周期由产品设置决定，并记录创建与到期时间。
- 审计、Task、Observation 和 Artifact 可采用不同保留策略。
- 用户主动删除必须可观察，并说明无法恢复。
- 清理任务可取消、幂等，并有删除数量和错误摘要。
- 密钥不进入数据库和 Artifact Store。

## 9. 数据模型变更清单

- 是否需要 Contract 变化？
- 是否有旧数据 backfill？
- 是否影响索引和启动时间？
- 是否需要额外磁盘空间？
- 是否可在事务内完成？
- 失败如何恢复？
- 是否影响降级？
- 测试 fixture 是否覆盖空库、旧库和异常中断？

## 10. 测试

- 空数据库升级到最新版本。
- 每个受支持旧版本升级。
- 重复运行迁移不会重复副作用。
- 迁移中断后行为可预测。
- 数据库过新时安全拒绝。
- Artifact 写入和数据库提交任一失败时保持一致。

## 11. 当前迁移

- `0001_task_store`：终态 TaskRun 与派生事件。
- `0002_task_executions`：异步执行状态、实时事件、幂等键和请求指纹。该迁移不改写已有 TaskRun；
  Runtime 启动后会将遗留非终态执行标记为中断，且不会调用设备或模型恢复动作。

ITER-0033 的 `device_session_id` 只增加到版本化 Task JSON。TaskExecution 读取旧 JSON 时使用
`null`，TaskRun 字段可选，因此不增加 SQL migration，也不回填历史任务的连接会话。
