# 迭代开发规范

> 文档状态：Active
> 更新日期：2026-07-26
> 适用范围：整个仓库

## 1. 目标

本规范定义 Mobile Agent 如何选择迭代目标、拆分任务、开发验证和完成交付。核心目标是在不降低
Contract、安全和可靠性要求的前提下，减少过度拆分、重复文档、重复全量测试和串行人工验收。

迭代以用户或产品能够感知的结果为单位，不以单个文件、类、Tool、接口或 Contract 为单位。

## 2. 工作单元

```text
Roadmap / Release
    → Iteration：一个可演示、可调用或可衡量的产品结果
        → Task：一项可独立实现和验证的工程交付
            → Test / Evidence：任务和迭代的完成证据
```

- **Iteration**：组合若干相关能力形成完整结果，例如“应用生命周期管理”。
- **Task**：实现一项能力或横切交付，例如 Adapter、MCP 接口、报告或测试。
- **Bug/Chore**：优先进入当前相关迭代，不因编号方便自动升级为新迭代。
- **ADR**：记录长期架构或信任决策，不是普通任务日志。

## 3. 默认粒度与节奏

一个正常迭代默认满足：

- 目标周期为 1–3 个工作日。
- 包含 3–6 个相关 Task。
- 产生一个可通过 UI、CLI、MCP、API 或报告验证的纵向结果。
- 开发完成后只安排一次集中全量验证和一次集中真机 E2E。
- 最多包含一个需要用户重新确认的高风险 E2E 阶段。

以上是默认预算，不是机械指标。超出时必须在 `plan.md` 说明原因；如果预计超过 5 个工作日或
8 个 Task，应按独立产品结果拆分。只有一个小 Task 的工作通常应并入当前迭代。

以下内容不应单独创建迭代：

- 单个字段、错误码、测试补充或文档澄清。
- 同一产品结果中的单个 Tool、REST 端点或 MCP Tool。
- 不改变公共行为的小型重构。
- 当前迭代验收发现的局部 Bug。

## 4. 创建新迭代的条件

同时满足以下条件时才创建新迭代编号：

1. 有独立且可描述的用户价值或工程结果。
2. 与当前 Active 迭代目标不同，合并会明显扩大范围。
3. 可以定义独立验收条件。
4. 至少包含两个实现 Task，或虽只有一个 Task 但属于紧急独立发布。

相关能力应优先打包。例如应用启动、停止、状态查询和高风险清除数据可以组成“应用生命周期管理”
迭代，而不是连续创建四个迭代。

## 5. 必需文档

每个迭代只维护一套文档：

```text
docs/iterations/NNNN-short-name/
├── plan.md
├── tasks.md
├── acceptance.md
└── retrospective.md
```

- `plan.md`：产品结果、范围、非目标、依赖、风险和兼容性。
- `tasks.md`：3–6 个默认 Task、Owner、状态和具体交付。
- `acceptance.md`：可执行或可观察的迭代级验收条件。
- `retrospective.md`：实际交付、验证指标、偏差、限制和后续行动。

四份文件在 Planned 阶段一次性建立。开发期间主要更新 `tasks.md`；只有范围、验收或长期决策变化
时才更新其他文档。不得为每个 Task 重复创建方案和复盘。

文档元数据与迭代生命周期分开表达：

```text
> 文档状态：Draft | Active | Superseded | Archived
> 迭代状态：Planned | Active | Verifying | Completed | Cancelled
```

完成后，四份迭代文档的文档状态为 `Active` 并冻结，迭代状态为 `Completed`。

## 6. 生命周期与门禁

```text
Proposed → Planned → Active → Verifying → Completed
                                  └──────→ Active（验收发现问题）
任意非终态 → Cancelled
```

### Planned

- 产品结果、范围和非目标明确。
- Task 与验收条件已定义。
- 已识别 Contract、迁移、ADR、真机和用户确认需求。

### Active

- 同一时间原则上只有一个主要 Active 迭代。
- Task 可以按稳定模块并行，但共享 Contract、注册表和迁移只有一个整合者。
- 新需求优先作为当前迭代 Task；明显改变产品结果时才创建下一迭代。

### Verifying

- 实现 Task 已完成。
- focused tests 已通过。
- Contract、用户文档和必要 ADR 已同步。
- 候选状态稳定后运行一次完整 `make check`。
- 相关真机场景按一个 E2E Suite 集中执行。

验收发现问题时回到 Active，只修复失败相关范围；运行相关测试后，在最终候选上重新运行一次完整
门禁。不得用连续重复执行全量测试替代定位。

### Completed

- 迭代级验收通过。
- `make check` 最终通过。
- 高风险设备写能力完成一次明确授权的真实 E2E；不得用 Fake 测试宣称真机完成。
- 非高风险且受环境限制的 E2E 可以明确记录为 deferred，但不能声称已通过。
- 复盘、索引和必要长期文档已更新。
- 已形成可审阅提交，不允许把多个已完成迭代长期堆积在同一未提交工作区。

## 7. 测试策略

### Task 开发期间

- 只运行本 Task 直接相关的单元、Contract、Adapter 或集成测试。
- Bug 修复先增加回归测试或等价复现。
- 不因每个文件修改重复运行完整测试集。

### 纵向链路接通后

- 运行该能力的跨层集成测试。
- 新 Tool/Skill 覆盖成功、参数错误、能力不足、策略拒绝、验证失败和超时语义。

### 迭代收尾

- 候选稳定后运行一次 `make check`。
- 真机 E2E 按 Suite 执行，集中验证同一产品结果中的多个场景。
- 模型驱动场景不使用固定路径回放替代在线规划。

## 8. 真机 E2E 与人工确认

- 真机 E2E 是迭代级验收 Task，不为每个内部模块单独创建等待点。
- 只读和 Low 风险场景可以批量执行。
- Medium/High 风险场景仍必须遵守各自确认边界；批量验收不能复用或伪造用户确认。
- High 风险两阶段操作必须先完成 Prepare、展示影响摘要并停止，再由用户对该摘要明确确认。
- 一个场景失败不自动提交替代任务；记录结果后继续执行不依赖该失败状态的安全场景。
- E2E 报告记录 task id、终态、错误码、outcome 和确定性后置验证，不以动作路径相似度作为成功标准。

## 9. ADR、Contract 与长期文档

以下变化才新增 ADR：

- 核心框架、存储、协议或 Runtime 变化。
- 模块依赖、Tool/Skill 或平台 Adapter 边界变化。
- 安全信任模型、风险策略或破坏性 Contract/API 变化。

兼容性新增字段、端点或能力仍需 Contract 和测试，但不自动要求 ADR。多个相关 Task 共享同一个
架构决策时，只创建一份 ADR。

README、架构和工程规范只在用户行为或长期真源发生变化时更新；Task 进度只写入迭代文档。

## 10. Git 与交付边界

- 开始迭代前检查工作区并确认已有修改归属。
- 一个提交应形成可审阅、可验证的完整结果；默认每个迭代 1–3 个提交。
- 不要求每个 Task 单独提交，也不把无关迭代混入同一提交。
- 当前迭代完成后，应先提交或明确移交，再进入下一迭代。
- 不允许连续完成两个以上迭代而没有清晰提交边界。

## 11. 快速通道

满足全部条件的修改可以作为当前迭代 Task 或独立 Hotfix，不新建完整迭代：

- 预计不超过半个工作日。
- 不新增 Capability、持久化状态或安全信任边界。
- 不产生破坏性 Contract/API 变化。
- 有明确回归测试或文档验证。

紧急安全或数据损坏修复可以打断当前迭代，但必须记录原因、独立验证和提交，完成后再恢复原迭代。

## 12. 效率指标

复盘至少记录：

- 从 Active 到 Verifying、Completed 的耗时。
- 计划 Task 数与新增/取消 Task 数。
- 完整 `make check` 执行次数。
- 人工确认/E2E 往返次数。
- 真机场景成功数与失败原因。
- 是否发生范围扩张或跨迭代未提交堆积。

指标用于发现流程瓶颈，不作为牺牲安全和测试质量的目标。

## 13. 反模式

- 一个 Tool、一个接口或一个错误码单独占用一个迭代。
- 先写大量未来设计，再寻找对应用户结果。
- 每完成一个 Task 都运行完整测试和真机验收。
- 为同一安全决策创建多份重复 ADR。
- Fake 测试通过后直接把真实设备能力标记为完成。
- 为了完成状态绕过确认、Policy、Lease、Session 或后置验证。
- 多个已完成迭代长期留在同一脏工作区。
